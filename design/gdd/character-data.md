# 角色数据 (Character Data)

> **Status**: Designed
> **Author**: user + agents
> **Last Updated**: 2026-03-27
> **Implements Pillar**: 粉丝幻想、策略发现

## Overview

角色数据系统是 V-Tacit 的基础数据层，定义了每个虚拟主播角色的**基础属性**（攻击、生命、定位）、**技能**（被动效果描述）、**羁绊标签**（所属团体/类型）和**稀有度**（星级）。

玩家通过商店看到角色卡牌、在棋盘上放置角色、观察到羁绊激活效果——所有这些交互的背后都是角色数据。没有这个系统，游戏无法识别"阿梓"是谁、她有什么能力、属于哪些羁绊。

本系统是纯粹的**数据定义层**，不包含游戏逻辑。逻辑由卡池管理、羁绊检测、属性计算等上游系统实现。

## Player Fantasy

### 情感目标

角色数据系统服务于 **虚拟主播粉丝的情感连接**：

1. **联动记忆点**：角色数据不仅包含数值，还包含直播中的经典故事/梗，让粉丝看到角色时想起那些记忆点
2. **羁绊互动**：当特定角色组合激活羁绊时，触发固定对话（如四喜丸子成员同时在场时的互动语音）
3. **戏剧性时刻**：最后一名角色被击败时，播放该角色的特殊语音

### 参考游戏

- **云顶之弈**：通过棋子羁绊传递英雄联盟背景故事
  - 羁绊激活时触发角色对话
  - 最后一名棋子被击败时的特殊语音
  - 让不熟悉LOL的玩家也能感受到角色故事
- **虚环**（内测中）：通过角色故事打动观众，虚拟主播"活"在游戏里

### 产品定位

这是 **面向玩家宣传的MVP产品**。角色数据不仅要"能用"，还要"能打动人"——让粉丝看到喜爱的虚拟主播"活"在游戏中，产生分享传播的欲望。

### MVP范围

- MVP阶段：角色属性、羁绊标签、技能描述（文字）
- MVP+阶段：羁绊激活对话、被击败语音
- 完整版：角色故事片段、语音包、互动动画

## Detailed Design

### Core Rules

#### 角色数据结构

每个角色由以下字段定义：

| 字段 | 类型 | 描述 | 示例 |
|------|------|------|------|
| `id` | string | 角色唯一标识（英文，用于代码引用） | `"azi"` |
| `display_name` | string | 显示名称（中文，用于UI展示） | `"阿梓"` |
| `rarity` | int | 稀有度/星级 (1-5) | `4` |
| `role` | enum | 战斗定位 | `"output"`, `"tank"`, `"support"`, `"core"`, `"warrior"`, `"mage"` |
| `base_attack` | int | 基础攻击力 | `65` |
| `base_health` | int | 基础生命值 | `750` |
| `synergy_tags` | array[string] | 羁绊标签列表 | `["VR", "singer", "moe_voice"]` |
| `skill` | object | 技能定义（见下方） | — |
| `flavor` | object | 情感内容（MVP+，见下方） | — |

#### 定位枚举 (`role`)

| 值 | 中文 | 描述 |
|---|------|------|
| `output` | 输出 | 高攻击，主要伤害来源 |
| `tank` | 坦克 | 高生命，吸收伤害 |
| `support` | 辅助 | 提供增益/减益效果 |
| `core` | 核心 | 综合能力强，队伍核心 |
| `warrior` | 战士 | 攻防平衡，持续作战 |
| `mage` | 法师 | 技能伤害为主 |

#### 技能结构 (`skill`)

采用 **触发器+效果分离** 设计：角色数据定义何时触发，羁绊效果系统定义触发什么。

```gdscript
skill = {
    "name": "分身协同",           # 技能名称
    "description": "每6次攻击生成分身协同攻击...",  # 文字描述
    "trigger": {
        "type": "on_attack_count",  # 触发类型
        "count": 6                   # 触发参数
    },
    "effect_id": "azi_clone_attack"  # 效果ID，由羁绊效果系统定义
}
```

**触发类型枚举** (`trigger.type`):

| 值 | 描述 | 触发参数 |
|---|---|---|
| `on_attack_count` | 攻击N次后触发 | `count`: 攻击次数 |
| `on_battle_start` | 战斗开始时触发 | 无 |
| `periodic` | 周期性触发（秒） | `interval`: 间隔时间 |
| `on_damage_taken` | 受到伤害时触发 | 无 |
| `passive` | 持续生效 | 无 |

**效果引用** (`effect_id`):
- 指向羁绊效果系统中定义的具体效果
- 角色数据只引用，不定义效果数值
- 多个角色可共用同一个效果ID

#### 情感内容结构 (`flavor`, MVP+)

```gdscript
flavor = {
    "story_hint": "上海KTV",           # 记忆点提示
    "defeat_line": "下次一定...",       # 被击败台词
    "synergy_lines": {                 # 羁绊激活对话
        "sixin_wanzi": "四喜丸子集结！"
    }
}
```

#### 数据存储格式

- **格式**: Godot Resource (`.tres`) 或 JSON
- **路径**: `assets/data/characters/character_[id].tres`
- **加载**: 游戏启动时全部加载到内存，通过 `id` 索引访问

### States and Transitions

角色数据是**静态只读数据**，本身没有状态转换。

#### 数据生命周期

```
[加载阶段]
游戏启动 → 加载所有角色数据 → 缓存在 CharacterRegistry → 供其他系统查询

[运行时]
其他系统请求角色数据 → CharacterRegistry 返回数据副本 → 请求方使用数据

[热更新（开发期）]
修改 .tres 文件 → 重新加载 CharacterRegistry → 新数据生效
```

#### 无状态设计原则

- 角色数据是只读的**配置数据**
- 运行时状态（如"当前攻击力"、"已触发次数"）由属性计算系统、战斗系统管理
- 角色数据只提供**基础值**，不存储变化
- 这确保了：
  - 数据安全：不会意外修改配置
  - 多实例支持：同一角色可在棋盘上出现多次，各自独立状态
  - 调参方便：修改配置文件即可调整数值，无需改代码

### Interactions with Other Systems

角色数据是 Foundation 层系统，被多个上层系统依赖。

#### 数据流向

| 系统 | 数据流向 | 使用方式 |
|------|----------|----------|
| **卡池管理** | 角色数据 → 卡池 | 读取所有角色，定义抽卡概率权重 |
| **羁绊检测** | 角色数据 → 检测器 | 读取角色的 `synergy_tags` 进行匹配 |
| **属性计算** | 角色数据 → 计算器 | 读取 `base_attack`, `base_health` 作为计算基础 |
| **角色渲染** | 角色数据 → 渲染器 | 读取 `display_name`, `rarity` 用于UI展示 |
| **商店UI** | 角色数据 → UI | 读取所有字段生成卡牌展示 |
| **羁绊效果** | 角色数据 → 效果系统 | 读取 `skill.effect_id` 查询具体效果 |

#### 接口定义

```gdscript
# CharacterRegistry.gd - 角色数据注册表（单例）
class_name CharacterRegistry

## 初始化：加载所有角色数据
func initialize() -> void

## 获取单个角色数据
func get_character(id: String) -> CharacterData

## 获取所有角色（用于卡池初始化）
func get_all_characters() -> Array[CharacterData]

## 按羁绊标签筛选
func get_by_synergy_tag(tag: String) -> Array[CharacterData]

## 按稀有度筛选
func get_by_rarity(rarity: int) -> Array[CharacterData]

## 按定位筛选
func get_by_role(role: String) -> Array[CharacterData]
```

#### 数据格式约定

- **输入**: 所有角色数据在游戏启动时从 `assets/data/characters/` 加载
- **输出**: 返回 `CharacterData` 资源对象，只读
- **不变性**: 调用方不应修改返回的数据对象；如需计算值，创建副本

## Formulas

角色数据系统本身不进行计算，但需要定义属性与稀有度的关系，供其他系统参考。

### 属性与稀有度关系

稀有度（星级）越高，基础属性越强。

| 稀有度 | 攻击力范围 | 生命值范围 | 出现概率 |
|--------|-----------|-----------|----------|
| 1星 | 40-55 | 500-600 | 30% |
| 2星 | 45-60 | 600-700 | 25% |
| 3星 | 55-65 | 700-900 | 25% |
| 4星 | 65-80 | 750-850 | 15% |
| 5星 | 60-90 | 1000-1200 | 5% |

### 属性基准公式

设计参考公式，用于指导数值设计：

```
基础攻击力 ≈ 40 + (稀有度 × 8) + 定位修正
基础生命值 ≈ 500 + (稀有度 × 100) + 定位修正
```

**定位修正**:

| 定位 | 攻击修正 | 生命修正 | 说明 |
|------|----------|----------|------|
| output | +15% | -10% | 高攻击，脆弱 |
| tank | -20% | +30% | 低攻击，高生存 |
| support | -10% | -5% | 辅助，属性偏低 |
| core | +10% | +15% | 综合强力 |
| warrior | +5% | +5% | 攻防平衡 |
| mage | +10% | -5% | 技能伤害为主 |

### 出现概率设计

**MVP阶段概率分布**:

```
总概率 = 100%
├── 1星: 30%
├── 2星: 25%
├── 3星: 25%
├── 4星: 15%
└── 5星: 5%
```

**设计意图**:
- 均衡分布，让玩家有机会体验各种稀有度的角色
- 5星角色稀有但不至于完全无法获得
- 后续版本可根据反馈调整

### 公式使用说明

以上公式为**设计参考**，实际数值以 `.tres` 文件中的配置为准：
- 属性计算系统读取 `base_attack`, `base_health` 进行计算
- 卡池管理系统读取 `rarity` 并应用出现概率
- 调整数值时直接修改配置文件，无需改代码

## Edge Cases

### 数据验证

| 情况 | 处理方式 |
|------|----------|
| 角色ID不存在 | `CharacterRegistry.get_character()` 返回 `null`，调用方需处理 |
| 羁绊标签为空 `[]` | 合法，表示该角色无羁绊标签 |
| 技能为空 `null` | 合法，表示该角色无主动技能（纯普攻角色） |
| 稀有度超出范围 (0 或 6+) | 数据验证时报错，阻止游戏启动 |
| 攻击力 ≤ 0 或 生命值 ≤ 0 | 数据验证时报错，阻止游戏启动 |
| `effect_id` 指向不存在的效果 | 运行时警告日志，技能不生效但不崩溃 |

### 重复角色处理

- 棋盘上**可以**放置同一角色的多个实例
- 每个实例独立计算属性和状态
- 角色数据是**只读模板**，不存储实例状态
- 实例状态由游戏状态系统管理

### 热更新边界

开发期间支持热更新角色数据：
- 修改 `.tres` 文件后调用 `CharacterRegistry.reload()`
- 已在棋盘上的角色实例**不受影响**（使用旧数据快照）
- 新放置的角色使用新数据
- 完整重置需要清空棋盘

### 数据一致性

- 所有角色数据在游戏启动时一次性加载
- 运行期间数据不可变，确保一致性
- 如需动态添加角色（如DLC），需要重新初始化整个注册表

## Dependencies

### 上游依赖

**无**。角色数据是 Foundation 层系统，不依赖任何其他游戏系统。

### 下游依赖

以下系统依赖角色数据：

| 系统 | 依赖类型 | 使用内容 |
|------|----------|----------|
| **卡池管理** | 强依赖 | 读取所有角色 → 定义抽卡池和概率 |
| **羁绊检测** | 强依赖 | 读取 `synergy_tags` → 检测羁绊组合 |
| **属性计算** | 强依赖 | 读取 `base_attack`, `base_health` → 计算战斗属性 |
| **角色渲染** | 强依赖 | 读取 `display_name`, `rarity` → UI展示 |
| **羁绊效果** | 弱依赖 | 读取 `skill.effect_id` → 查询技能效果 |

### 接口契约

角色数据向下游系统承诺的接口稳定性：

| 接口 | 稳定性 | 说明 |
|------|--------|------|
| `get_character(id)` | 稳定 | 不会改变签名 |
| `get_all_characters()` | 稳定 | 不会改变签名 |
| `CharacterData` 字段 | 扩展性 | 可新增字段，不会删除或重命名现有字段 |
| `skill.trigger` 格式 | 稳定 | 触发类型枚举可扩展，现有值不变 |

### 数据格式版本控制

如果未来数据格式变更（如添加新字段），策略：
1. 新字段设置默认值，兼容旧数据
2. 版本号字段 `version` 用于追踪格式版本
3. 加载时进行格式验证和迁移

## Tuning Knobs

以下是策划可以调整的参数，无需修改代码。

### 单角色调参

| 参数 | 文件位置 | 安全范围 | 过高风险 | 过低风险 |
|------|----------|----------|----------|----------|
| `base_attack` | `.tres` | 30-100 | 角色过强，破坏平衡 | 角色无存在感 |
| `base_health` | `.tres` | 400-1500 | 坦克过强，战斗拖长 | 角色过脆 |
| `rarity` | `.tres` | 1-5 | 影响出现概率和玩家体验 | 影响出现概率和玩家体验 |
| `synergy_tags` | `.tres` | 任意标签 | 羁绊组合过多，策略分散 | 角色难以融入羁绊 |
| `skill.trigger.count` | `.tres` | 1-10 | 技能触发过慢 | 技能触发过快 |
| `skill.trigger.interval` | `.tres` | 1-30秒 | 触发过慢 | 触发过快 |

### 全局调参

| 参数 | 位置 | 默认值 | 说明 |
|------|------|--------|------|
| 出现概率分布 | 卡池管理 | 30%/25%/25%/15%/5% | 各稀有度出现概率 |
| 定位修正系数 | 属性计算 | 见Formulas节 | 影响最终战斗属性 |

### 调参建议

1. **数值迭代**: 先用占位数值跑通流程，再逐步调整平衡
2. **日志追踪**: 战斗系统应输出详细日志，便于验证数值效果
3. **A/B测试**: 完整版可考虑对不同玩家群体使用不同数值
4. **社区反馈**: 关注玩家对角色强度的反馈，及时调整

### 调参风险

- **连锁效应**: 修改一个角色的数值可能影响整个羁绊组合的价值
- **锚点效应**: 玩家会对"标准强度"形成预期，大幅调整会引起不满
- **策略坍缩**: 如果某个角色明显过强，会导致所有玩家都选择它
